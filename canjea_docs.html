0. Antes de empezar

  1. Escribir por WhatsApp al +51 973 581 378 con el nombre del negocio y para qué se va a usar la API.
  2. Canjea crea la cuenta en producción —no hay sandbox— con S/ 3 (o USD 1) de saldo de prueba: alcanza para ejercitar el flujo completo con una compra real pequeña antes de cargar saldo en serio.
  3. La clave se genera desde el propio panel del distribuidor, en Mi cuenta → Claves de API, con el PIN de la cuenta — Canjea habilita esa sección al crear la cuenta. Se muestra una sola vez (§2). Se pueden tener hasta 3 activas, para rotar sin corte, y cada una se revoca por separado desde el mismo lugar.
  4. Con la integración lista, el saldo real se carga por los métodos normales del panel del distribuidor.

Productos de prueba

Para ejercitar el flujo completo sin entregar nada a nadie, hay dos skus que responden por libreto. No aparecen en GET /catalog: se llega a ellos por sku, y solo por sku. Cuestan S/ 0,10 (o su equivalente en USD) y se cobran de verdad, para que el saldo se mueva como en una compra real.

sku tipo requires_player_id can_verify_player
test-topup recarga por ID true true
test-code entrega de código false false

En test-topup, el player.id decide el resultado:

player.id POST /verify-player POST /orders
1000 VERIFIED · «Jugador Prueba» 200 · COMPLETED
1001 INVALID_ID 400 PLAYER_NOT_FOUND · external_id_reusable: true
1002 NAME_NOT_CONFIRMED 200 · COMPLETED
1003 VERIFIED 409 OUT_OF_STOCK · external_id_reusable: true
1004 VERIFIED 200 · PROCESSING, y COMPLETED a los 15 s (para practicar el sondeo con GET /orders/{ref})
1005 VERIFIED 400 ACCOUNT_RESTRICTED · external_id_reusable: false
1006 VERIFIED 502 PROVIDER_REJECTED · external_id_reusable: false
cualquier otro INVALID_ID 400 PLAYER_NOT_FOUND · external_id_reusable: true

test-code acepta cualquier compra y devuelve un redeem_code con la forma TEST-XXXX-XXXX-XXXX, que no se canjea en ningún lado.

Los ids 1005 y 1006 dejan la referencia quemada a propósito (external_id_reusable: false): son los dos casos donde el contrato pide consultar GET /orders/{ref} en vez de reintentar, y son los que más cuesta practicar con productos reales. ORPHANED no se simula: es la única respuesta que requiere una persona.

Formato de las peticiones. Todas las que llevan cuerpo van con Content-Type: application/json. Sin esa cabecera el cuerpo no se lee, y el error que se recibe es el del campo que faltó, no uno de formato. Un cuerpo que no es JSON válido responde 400 INVALID_JSON.

No hay webhooks. El estado de una orden se consulta con GET /orders/{external_id} (§7); nada llama al integrador.

Productos con entrega manual

Algunos productos los entrega una persona, no el sistema. Lo vas a ver en el catálogo:

"delivery": {
  "mode": "human",
  "hours": "08:00-22:00 America/Lima",
  "eta_minutes": null
}

Cuando mode es "human":

  • La orden se acepta y queda en PROCESSING hasta que alguien la resuelva. player se ignora: estos productos no llevan id de jugador.
  • Entregas de lunes a domingo, 08:00–22:00 hora de Lima. Fuera de ese horario la orden espera al siguiente. En días excepcionales puede demorar más.
  • eta_minutes es null hasta que tengamos una muestra suficiente para publicar un tiempo medido. No publicamos estimaciones sin datos.

Esos productos piden datos del cliente final. El catálogo te dice cuáles:

"required_fields": [
  { "key": "...", "label": "...", "type": "email|text|tel|checkbox",
    "required": true, "sensitive": false, "help": "..." }
]

Mandalos en fields al crear la orden ({ key: valor }; un checkbox como booleano). Si falta uno recibís FIELD_REQUIRED; si el formato no corresponde (hoy: un tel que no es un teléfono de 9 a 15 dígitos), FIELD_INVALID. En los dos casos con detail.field, sin cargo, y tu external_id sigue siendo reutilizable.

Los campos con sensitive: true se guardan cifrados de nuestro lado y se borran al resolverse el pedido, o a las 24 horas si nadie lo resolvió. Lo que hagas con esos datos de tu lado es tu responsabilidad.

Consultar una orden manual. Toda orden de un producto human —en la respuesta del POST y en GET /orders/{external_id}— lleva el bloque delivery con dos campos más, que cambian con el reloj:

"delivery": {
  "mode": "human",
  "hours": "08:00-22:00 America/Lima",
  "eta_minutes": null,
  "outside_hours": true,
  "resumes_at": "2026-09-17T08:00:00-05:00"
}
  • outside_hours: true → estamos fuera del horario de atención y resumes_at dice cuándo volvemos a atender. No consultes antes de esa hora: no va a haber cambio.
  • outside_hours: false → estamos atendiendo. resumes_at es null si la orden llegó dentro del horario; si llegó de noche, es la apertura que ya pasó. En los dos casos, consultar cada pocos minutos alcanza.

1. Modelo

Una cuenta de API es una cuenta de distribuidor que habla HTTP: mismo saldo, misma moneda, mismos precios que si se comprara por el panel. No hay un catálogo distinto ni una lista de precios paralela.

  • El saldo es prepago. Cada compra lo descuenta. Si no alcanza, la compra se rechaza y no se cobra nada.
  • La moneda se fija al crear la cuenta (PEN o USD) y no cambia. Todos los precios de todas las respuestas vienen en esa moneda, y toda respuesta que trae un precio lo dice en currency. Las que no traen precios —POST /verify-player y los errores— no la incluyen.
  • Los montos son cadenas, con punto decimal y dos decimales ("4.95"), nunca números JSON. Ver §6.

2. Autenticación

Cabecera Authorization con la clave, en todas las peticiones:

Authorization: Bearer ck_live_xxxxxxxxxxxxxxxxxxxxxxxx

curl -H "Authorization: Bearer $CANJEA_API_KEY" \
     https://api.canjea.me/api/v1/balance

🔴 No hay entorno de pruebas. Solo existe el prefijo ck_live_ porque solo existe producción: no hay sandbox ni claves de test. La integración se hace contra el sistema real, con una cuenta de saldo acotado y los productos de prueba de §0, que ejercitan cada rama del contrato sin entregar nada a nadie.

Lo decimos de entrada porque cambia cómo se planifica el trabajo, y porque una recarga entregada no se puede revertir. Para probar sin entregar nada, GET /balance, GET /catalog, GET /catalog/{sku}, GET /orders y POST /verify-player son de solo lectura y no mueven un centavo. GET /catalog/{sku} y POST /verify-player sí consultan al proveedor, y por eso el segundo tiene su propio límite (§3, §7).

  • La clave se genera desde Mi cuenta → Claves de API del panel del distribuidor, con el PIN de la cuenta, y se muestra una sola vez: no se puede recuperar después, solo revocar y generar otra.
  • Una cuenta puede tener hasta 3 claves activas a la vez, lo que permite rotarlas sin ventana de corte: se genera la nueva, se despliega, y solo entonces se revoca la vieja (también desde el panel, con el PIN).
  • La revocación es inmediata — no hay caché ni TTL que esperar.

Sin clave, con una clave inválida, revocada o de una cuenta desactivada, la respuesta es siempre la misma:

{ "ok": false, "code": "UNAUTHORIZED", "message": "Clave de API inválida o revocada" }

Los cuatro casos comparten el mismo código: la respuesta no distingue entre ellos. Si aparece de repente en producción, lo primero a verificar es si la clave fue revocada o rotada.

3. Límite de peticiones

El límite es por clave, no por IP, y se configura por cuenta (60 por minuto salvo que se acuerde otro). Cada respuesta trae las cabeceras estándar RateLimit-Limit, RateLimit-Remaining y RateLimit-Reset (Reset son segundos hasta que se reinicia la ventana, no una fecha). El 429 trae además Retry-After, en segundos.

Las llamadas a POST /verify-player tienen un límite propio más bajo (§7) y también descuentan de este.

Al superarlo:

HTTP 429
{ "ok": false, "code": "RATE_LIMIT_EXCEEDED", "message": "Superaste el límite de peticiones por minuto de tu clave" }

Un 429 es transitorio: esperar los segundos de Retry-After (o de RateLimit-Reset) y reintentar es correcto. No hace falta espera exponencial: la cabecera ya dice cuánto.

4. Contrato de errores

Todo error tiene la misma forma:

{ "ok": false, "code": "INSUFFICIENT_BALANCE", "message": "...", "detail": { } }

Tres reglas que conviene tener presentes al integrar:

  1. code es estable y es lo que hay que ramificar. No cambia sin aviso ni versión nueva.
  2. message es cortesía y puede cambiar en cualquier momento. Sirve para logs y para mostrarle algo a un humano; no para decidir. Nunca parsearlo.
  3. El código HTTP significa algo: 200 solo si la operación salió bien. Nunca devolvemos 200 con un fracaso adentro. La única excepción deliberada es POST /verify-player: sus cuatro result —incluido «ese id no existe»— llegan con 200, porque la consulta funcionó y el resultado ES la respuesta (§7).

detail es opcional. Hoy solo lo trae PRICE_CHANGED (current_price y currency); ningún otro código lo incluye. Los errores que decide la lógica de POST /orders agregan además external_id_reusable en la raíz (§8).

5. El sku

El identificador de un producto en el catálogo.

🔴 Es opaco: no parsearlo, no derivar nada de su forma. Hoy algunos tienen la forma producto-123 y otros no; eso es un detalle interno y puede cambiar. Tratarlo como una cadena sin estructura.

Dos garantías, y las dos importan si se va a cachear el catálogo:

  • Un sku puede desaparecer — si el producto deja de venderse. A partir de ahí devuelve 404 SKU_NOT_FOUND. Un sku que desaparece no vuelve con otro significado.
  • Un sku nunca cambia de significado. No se reasigna. Si responde, es el mismo producto que era.

En la práctica: se puede guardar el sku en el sistema propio y mapearlo contra el catálogo propio con confianza. Lo que no se puede es deducir nada de su texto ni construir uno a mano.

Qué productos aparecen

El catálogo lista solo lo que la API puede entregar. Un producto cuya entrega necesita datos que este contrato no tiene cómo recibir (por ejemplo, los que se cargan entrando a la cuenta del cliente con su correo y contraseña) no se lista, y su sku responde 404 SKU_NOT_FOUND en GET /catalog/{sku}, POST /verify-player y POST /orders. Lo mismo pasa con un producto que Canjea decide no exponer por la API. En los dos casos la regla es la misma: lo que el catálogo no lista, la orden no acepta. Si un sku que se veía deja de verse, tratarlo como discontinuado.

6. Precios

Cada producto trae dos números distintos:

campo qué es
price lo que se le cobra a la cuenta. Nunca es null
suggested_retail_price precio de venta al público de referencia. Puede ser null

suggested_retail_price es un ancla orientativa que fija Canjea, no un precio impuesto: se puede revender al precio que se desee.

Todos los montos son cadenas con punto decimal y dos decimales ("4.95"), tanto en las respuestas como en expected_price. Un número JSON se acepta, pero el contrato es la cadena; "4,95" con coma se rechaza con 400 INVALID_PARAMETER.

De dónde sale price, y por qué puede ser aproximado

price se calcula a partir del costo que el proveedor le cobra a Canjea. Ese costo se conoce en tres momentos distintos, y los tres pueden dar un número distinto para el mismo sku en el mismo minuto — ninguno es un error:

momento qué costo usa price_is_estimated
GET /catalog el último costo guardado de cada producto. Resuelve todo el catálogo de una vez y no consulta a ningún proveedor dice si ese costo guardado es exacto para ese producto. No incluye price_is_estimated_reason: la razón es siempre la misma, no hubo consulta
GET /catalog/{sku} consulta el costo en vivo al proveedor, con una caché de 60 s (cost_checked_at dice cuándo). Si el proveedor no responde o no tiene consulta en vivo, cae al guardado false si la consulta respondió; true si no, con la razón en price_is_estimated_reason
POST /orders el costo que tenga la compra en ese instante: en vivo si el proveedor lo da en ese momento, guardado si no no se devuelve; decide la tolerancia de expected_price (§7)

El guardado envejece hasta que el proveedor avisa un cambio; el vivo es el de ese segundo; la compra cobra lo que cuesta cuando se ejecuta.

  • false → el precio es exacto: es el que va a cobrar la compra si el costo no se mueve entre esta consulta y esa.
  • true → es aproximado. Puede moverse unos centavos.

🔴 Pedir GET /catalog/{sku} NO garantiza precio exacto: hay que mirar price_is_estimated. Puede venir true igual, y price_is_estimated_reason dice por qué — son dos causas con acciones opuestas:

price_is_estimated_reason qué pasó qué hacer
null el precio es exacto usarlo como expected_price
consulta_en_vivo_fallida el proveedor no respondió; se usó el último costo guardado transitorio — volver a pedirlo más tarde
proveedor_sin_consulta_en_vivo ese proveedor no expone costo en vivo permanente para ese sku — no volver a pedirlo aquí: GET /catalog da exactamente lo mismo. Conviene recordar qué skus lo devolvieron para no repetir la llamada

Ante una consulta de costo fallida devolvemos un precio aproximado en vez de un error, porque la compra funciona igual en ese caso: un error diría "no se puede" sobre un producto que sí se puede comprar. Por eso hay que mirar el flag y no asumirlo por el código HTTP.

Qué garantiza expected_price, entonces: un techo. Si el precio de la compra supera lo esperado más allá de la tolerancia (§7), se rechaza sin cobrar. No garantiza el centavo exacto: para eso está el price que devuelve la propia compra.

7. Endpoints

GET /catalog

Todo el catálogo disponible para la cuenta, en la moneda de la cuenta.

{
  "ok": true,
  "currency": "USD",
  "products": [
    {
      "sku": "rob500",
      "name": "500 Robux",
      "game": "rb",
      "game_name": "Roblox",
      "price": "4.95",
      "suggested_retail_price": "5.85",
      "price_is_estimated": true,
      "currency": "USD",
      "requires_player_id": false,
      "can_verify_player": false,
      "redeem_instructions": "Las tarjetas de regalo de Roblox se pueden canjear en roblox.com/redeem …",
      "delivery": { "mode": "instant" },
      "required_fields": []
    }
  ]
}

requires_player_id indica si al comprar hay que enviar player.id (recarga directa a una cuenta) o no (entrega de un código).

delivery dice quién entrega y cuándo, antes de comprar. mode es instant (un proveedor o nuestro inventario, en segundos) o human: lo entrega una persona de Canjea, y ahí el bloque trae además el horario:

"delivery": { "mode": "human", "hours": "08:00-22:00 America/Lima", "eta_minutes": null }

Entregas de lunes a domingo, 08:00–22:00 hora de Lima. Fuera de ese horario la orden se acepta y espera al siguiente horario de atención. En días excepcionales puede demorar más.

Una orden human nace en PROCESSING y así queda hasta que la persona la resuelva — minutos dentro del horario, o hasta la próxima apertura si llegó de noche. Se consulta con GET /orders/{external_id}, que en esos productos trae este mismo bloque con outside_hours y resumes_at (ver ese endpoint). eta_minutes viene null mientras no haya un tiempo medido que publicar; si algún día trae un número, es un promedio real dentro del horario, no una promesa.

required_fields es la lista de datos del cliente final que ese sku exige en fields al comprar (POST /orders). Vacía en todo lo que no los pide. Cada entrada:

{ "key": "clientEmail", "label": "Correo de Supercell del cliente", "type": "email",
  "required": true, "sensitive": false, "help": "La opción «Iniciar sesión» solo es válida para Supercell ID." }

type es email, text, tel o checkbox. sensitive: true marca una credencial (una contraseña): Canjea la guarda cifrada y la borra al resolver la orden — no queda en ningún historial. Lo que el integrador haga con el dato de su cliente antes de enviarlo es su responsabilidad. help es el texto de ayuda que ve el distribuidor en el panel de Canjea al llenar ese campo; conviene mostrarlo igual.

redeem_instructions es el texto para el cliente final: cómo canjear el código que entrega ese producto. Viene solo en productos de código; en una recarga directa es null (no hay nada que canjear). Un producto de código puede traer null si todavía no tiene texto cargado. Está en español, puede tener varios párrafos separados por \n, y cambia poco: conviene guardarlo junto al sku y mostrarlo al lado del redeem_code. Es el mismo texto que ve el distribuidor en el panel de Canjea al vender.

can_verify_player indica si se puede consultar el nombre del jugador antes de cobrarle, con POST /verify-player.

game es el código estable del juego —opaco, como el sku— y game_name su nombre para mostrar. Sirven para agrupar; no hay una lista de juegos aparte, la lista es este catálogo.

Los dos campos se leen juntos, porque solos son ambiguos:

requires_player_id can_verify_player qué significa
false false Es un código. No lleva id de jugador.
true true Lleva id y es posible verificarlo antes de comprar.
true false Lleva id y no hay forma de verificarlo.

La combinación false / true no existe: un código no tiene una cuenta que verificar.

Hoy la tercera fila son 79 de los 299 productos, concentrados en nueve juegos de un proveedor que no expone verificación. Conviene que la interfaz lo contemple desde el principio en vez de descubrirlo vendiendo: en esos productos el id viaja tal cual y un id equivocado se entrega a la cuenta equivocada, sin forma de revertirlo.

Un producto que no aparece en esta lista no se puede comprar con la cuenta. Los productos de monto libre —donde el cliente elige cuánto cargar, como un saldo en otra moneda— no aparecen y no se venden por la API: pedir su sku a mano responde 400 UNSUPPORTED_TYPE.

GET /catalog/{sku}

Un solo producto, con el costo consultado en el momento. Es el endpoint a usar justo antes de comprar cuando se necesita el precio exacto.

{
  "ok": true,
  "currency": "USD",
  "product": {
    "sku": "rob500",
    "name": "500 Robux",
    "game": "rb",
    "game_name": "Roblox",
    "price": "4.95",
    "suggested_retail_price": "5.85",
    "price_is_estimated": false,
    "price_is_estimated_reason": null,
    "cost_checked_at": "2026-08-05T23:20:38.958Z",
    "currency": "USD",
    "requires_player_id": false,
    "can_verify_player": false,
    "redeem_instructions": "Las tarjetas de regalo de Roblox se pueden canjear en roblox.com/redeem …",
    "delivery": { "mode": "instant" },
    "required_fields": []
  }
}

delivery y required_fields son los mismos que en GET /catalog (ver ahí qué significan y cómo se ven en un producto que entrega una persona).

requires_player_id, can_verify_player y redeem_instructions significan lo mismo que en GET /catalog, y los dos primeros se leen juntos igual — ver la tabla de más arriba.

cost_checked_at es cuándo se consultó el costo (ISO-8601, UTC), o null si no hubo consulta. Puede ser de hasta un minuto atrás: el costo se cachea 60 segundos. La diferencia real en ese lapso es de centésimas de punto porcentual.

⏱️ Este endpoint puede tardar cerca de un segundo. Medido: entre 130 ms y 900 ms según el producto. Configurar un timeout de al menos 5 segundos y tenerlo en cuenta si se lo llama dentro de un flujo donde un cliente final está esperando.

Errores: 404 SKU_NOT_FOUND si el sku no existe o el producto dejó de venderse.

POST /verify-player

¿Existe esta cuenta, y cómo se llama? Se responde antes de cobrar.

→  { "sku": "ff341", "player": { "id": "10303085282" } }

←  { "ok": true, "result": "VERIFIED",
     "player": { "id": "10303085282", "name": "Okarun8828" } }

Para juegos que lo necesiten, player acepta además server y zone_id.

Los cuatro resultados

Todos llegan con 200, incluido "ese id no existe". La llamada funcionó; el resultado es la respuesta.

result qué hacer
VERIFIED Mostrar player.name al usuario y continuar.
INVALID_ID Esa cuenta no existe. No comprar: pedir al usuario que lo corrija. message trae el motivo del proveedor cuando lo envía.
NAME_NOT_CONFIRMED El proveedor acepta el id pero no devolvió el nombre. No es un id inválido — pasa con cuentas reales. Pedir al usuario que lo confirme antes de seguir.
NO_VERIFIER Ese juego no tiene forma de verificar. El id viaja tal cual al comprar.

Las cuatro formas, tal como llegan — solo VERIFIED trae player; en las otras tres el nombre no existe y no se manda ni como null:

{ "ok": true, "result": "VERIFIED", "player": { "id": "10303085282", "name": "Okarun8828" } }
{ "ok": true, "result": "INVALID_ID", "message": "Esa cuenta no existe" }
{ "ok": true, "result": "NAME_NOT_CONFIRMED", "message": "El proveedor acepta el id pero no devolvió el nombre..." }
{ "ok": true, "result": "NO_VERIFIER", "message": "Este juego no tiene forma de verificar la cuenta..." }

🔴 No tratar INVALID_ID como un error de red. Es la respuesta más valiosa de este endpoint: es la que evita la recarga a una cuenta que no existe. Por eso viaja como 200 y no como error HTTP — para que no caiga en el mismo catch que un timeout.

Errores (aquí sí)

HTTP code cuándo
400 PLAYER_ID_REQUIRED falta player.id
400 UNSUPPORTED_TYPE el producto es un código y no lleva id
404 SKU_NOT_FOUND ese sku no existe o no está activo
429 RATE_LIMIT_EXCEEDED ver abajo
503 SERVICE_UNAVAILABLE no pudimos consultar al proveedor. Intentar de nuevo. Solo en este endpoint el 503 habla del proveedor; en el resto de la API significa que no se pudo verificar la clave (§9)

Dos cosas a tener en cuenta

Tiene su propio límite, más bajo que el general. Cada llamada consulta al proveedor, no a nuestra base. El techo son 20 por minuto (el general son 60), configurable por cuenta — escribir a soporte si se necesita más (§12). Estas llamadas descuentan también del límite general.

Puede tardar. Una cuenta que existe responde en menos de 2 segundos, pero una que no existe puede tardar hasta 20. Esa espera es la señal: no cortarla antes de tiempo o se perderán justamente los INVALID_ID. Usar un timeout de al menos 30 s para esta llamada.

POST /orders ya valida el id por su cuenta —cuando el proveedor puede hacerlo, es decir con can_verify_player: true— y rechaza si esa cuenta no existe, así que verificar antes no es lo que protege de una recarga a un id equivocado — eso ya está cubierto. En los productos con can_verify_player: false nadie puede validarlo, ni este endpoint ni la compra: el id viaja tal cual (ver la tabla de GET /catalog).

Para qué sirve entonces: para mostrarle el nombre al usuario antes de que pague, dentro del propio flujo. Es la diferencia entre "confirma que eres tú" y descubrir el error después.

⚠️ Llamar a los dos significa preguntarle dos veces al mismo proveedor. Cuando la cuenta existe, la segunda consulta suma alrededor de medio segundo a la compra (los 20 s son solo para las que no existen, y esas la compra las rechaza igual). Vale la pena si el nombre se le muestra al usuario; no vale si solo se descarta.

La compra.

  "sku": "rob500",

{ "sku": "ff341", "external_id": "PEDIDO-2026-00185", "expected_price": "...",

En un producto de código, player se ignora si se envía.

campo
sku obligatorio del catálogo
external_id obligatorio identificador único propio de este pedido. 1-80 caracteres A-Z a-z 0-9 . - _. Único por cuenta y sensible a mayúsculas: PEDIDO-1 y pedido-1 son dos pedidos distintos
expected_price opcional el precio obtenido del catálogo. Ver abajo
player.id obligatorio si requires_player_id el ID de la cuenta del jugador, como cadena (un número se acepta y se convierte)
player.server según el juego servidor, cuando el juego lo pide
player.zone_id según el juego zona, cuando el juego la pide. Si vienen los dos, se usa server
fields obligatorio si el sku tiene required_fields objeto { key: valor } con los datos del cliente final que lista required_fields de ese sku en el catálogo. Un checkbox va como booleano. Claves que no están en la lista se ignoran

Para un producto que entrega una persona (delivery.mode: human), el cuerpo lleva fields en vez de player:

{ "sku": "bs80", "external_id": "PEDIDO-2026-00190",
  "fields": { "clientEmail": "cliente@gmail.com", "clientOtp": "482913", "clientWhatsapp": "51999888777" } }

Falta un campo requerido → 400 FIELD_REQUIRED; un teléfono que no lo es → 400 FIELD_INVALID. En los dos, detail.field dice cuál, y no se cobró nada: la referencia se puede reusar con el cuerpo corregido. La orden nace en PROCESSING con el bloque delivery de la orden (ver más abajo), también si llegó fuera de horario — no se rechaza, espera.

Respuesta exitosa:

{
  "ok": true,
  "order": {
    "external_id": "PEDIDO-2026-00184",
    "sku": "rob500",
    "status": "COMPLETED",
    "price": "4.95",
    "currency": "USD",
    "redeem_code": "RA-7E6CZMYLVBLVAKPJ",
    "remaining_balance": "100.05",
    "delivery": { "mode": "instant" }
  }
}

delivery en la orden es el mismo bloque del catálogo, y en un producto human agrega dos campos que cambian con el reloj: outside_hours (si en este momento estamos fuera del horario de atención) y resumes_at (cuándo se retoma la atención, en hora de Lima). Un resumes_at en el pasado con la orden todavía en PROCESSING significa que la atención ya se retomó y la orden sigue esperando — puede pasar en un día excepcional; es visible a propósito.

"delivery": { "mode": "human", "hours": "08:00-22:00 America/Lima",
              "outside_hours": true, "resumes_at": "2026-09-17T08:00:00-05:00", "eta_minutes": null }

Cuándo volver a preguntar, para no consultar cada 5 segundos durante 10 horas: si outside_hours es true, no antes de resumes_at; dentro del horario, cada pocos minutos alcanza.

redeem_code viene poblado solo en productos que entregan un código. En una recarga directa a la cuenta del jugador es null, y eso es lo correcto: no hay ningún código que entregarle al cliente final, la recarga ya se acreditó.

Las instrucciones de canje no viajan en la orden: están en el catálogo, como redeem_instructions de cada sku (GET /catalog y GET /catalog/{sku}). Son las mismas para todas las compras de ese sku, así que se guardan una vez junto al sku y se muestran al lado del redeem_code.

Si la compra sigue en curso cuando la petición ya tiene que responder, el POST devuelve 200 con status: PROCESSING y el mismo objeto que una completada: el precio ya se cobró y el saldo ya bajó, lo único que falta es la confirmación del proveedor. redeem_code viene null hasta entonces.

{ "ok": true,
  "order": { "external_id": "PEDIDO-2026-00184", "sku": "rob500", "status": "PROCESSING",
             "price": "4.95", "currency": "USD", "redeem_code": null, "remaining_balance": "100.05" } }

Y si la referencia ya se había resuelto antes, vuelve la respuesta original con "replay": true en la raíz, junto a ok (§8).

⏱️ Tiempos de POST /orders — configurar el timeout alto

🔴 Es la advertencia más importante para integrar.

En productos con requires_player_id: true, la compra valida el ID contra el sistema del juego antes de cobrar, y esa validación puede tardar hasta 25 segundos cuando el sistema del juego está lento. Sumado al resto de la compra, una petición puede tardar más de 30 segundos.

Configurar el timeout del cliente HTTP en 60 segundos o más.

Un timeout corto es el peor escenario posible: el lado del integrador corta la conexión, pero la compra sigue procesándose de nuestro lado. Se queda sin saber si se cobró o no. Si aun así ocurre, la salida está en §8: consultar GET /orders/{ref} — nunca reintentar el POST a ciegas.

Los productos de código (requires_player_id: false) no pasan por esa validación y responden mucho más rápido, pero el timeout alto conviene igual: el mismo cliente HTTP sirve para los dos.

expected_price — protección contra un precio que se movió

Para qué sirve: entre que se consulta el catálogo y se compra pasan segundos o minutos, y el precio puede haberse movido. Sin expected_price, se compraría al precio nuevo sin saberlo y el margen saldría distinto del calculado. Con él, la decisión de aceptar o no ese precio nuevo vuelve a ser del integrador.

Si se envía y el precio real subió por encima de lo esperado, la compra se rechaza con 409 PRICE_CHANGED y el precio actual en detail:

{ "ok": false, "code": "PRICE_CHANGED",
  "message": "El precio cambió desde que consultaste el catálogo",
  "external_id_reusable": true,
  "detail": { "current_price": "5.10", "currency": "USD" } }

Si el precio bajó, la compra sigue: nunca se rechazará una compra por salir más barata.

Se compara contra price — lo que se le cobra a la cuenta— y no contra suggested_retail_price. Los dos vienen en la misma respuesta del catálogo, así que vale decirlo explícito: si se envía el sugerido, la comparación es contra otro número y se rechazarán compras legítimas.

La tolerancia la decidimos nosotros, en el momento de la compra

cómo resolvió el precio la compra tolerancia
exacto estricta — cualquier subida rechaza
aproximado 1 %

El 1 % existe porque un precio aproximado se mueve por definición: sin tolerancia rechazaría compras legítimas de forma permanente.

🔴 Lo que decide la tolerancia es el estado del costo al comprar, no lo que devolvió el catálogo. Son dos momentos distintos y pueden no coincidir: GET /catalog/{sku} consulta el costo en vivo y por eso puede devolver price_is_estimated: false, mientras que la compra resuelve con el costo guardado y aplica el 1 %.

Consecuencia práctica: no hay forma de garantizar comparación estricta desde el lado del integrador. expected_price es un techo con hasta 1 % de juego, no un precio pactado.

Si importa el centavo, la respuesta de la compra trae el precio efectivamente cobrado y el saldo resultante — verificar ahí, no en lo enviado.

Enviar el número tal como lo devolvió el catálogo: "4.95", cadena con punto decimal. "4,95" con coma se rechaza con 400 INVALID_PARAMETER en vez de ignorarse en silencio.

GET /orders/{external_id}

El estado de una orden por la referencia propia.

{
  "ok": true,
  "order": {
    "external_id": "PEDIDO-2026-00184",
    "sku": "rob500",
    "name": "500 Robux",
    "game": "rb",
    "status": "COMPLETED",
    "price": "4.95",
    "currency": "USD",
    "redeem_code": "RA-7E6CZMYLVBLVAKPJ",
    "created_at": "2026-08-05T23:20:38.958Z"
  }
}

Es el endpoint que hay que consultar si se perdió la respuesta del POST — un timeout de red, un proceso que se cayó.

Las tres respuestas posibles, y qué hacer con cada una

1 · La orden existe → 200 con el objeto de arriba. Revisar status (§8) y actuar según eso. Es el caso normal.

2 · PROCESSING → 200, pero con un objeto reducido: solo la referencia y el estado.

{ "ok": true, "order": { "external_id": "PEDIDO-2026-00184", "status": "PROCESSING" } }

La compra está siendo procesada en este mismo momento. Consultar de nuevo cada 5–10 segundos. Si a los 5 minutos de haber salido al proveedor sigue sin resolverse, pasa a ORPHANED (abajo). No reintentar el POST: la orden está viva y un reintento no la acelera.

3 · ORPHANED → 409.

{ "ok": false, "code": "ORPHANED",
  "message": "La orden quedó a mitad y necesita revisión. No reintentes con esta referencia.",
  "external_id_reusable": false }

La orden salió a procesarse y quedó sin resolver más allá del tiempo esperado. Requiere revisión de nuestro lado: escribir a soporte con la referencia por WhatsApp al +51 973 581 378 (§12).

🔴 No reintentar con esa referencia ni generar una nueva para el mismo pedido. Podría terminar cobrándose dos veces. Es la única respuesta de toda la API que pide intervención humana.

Y si no hay ni orden ni intento con esa referencia: 404 ORDER_NOT_FOUND — el POST nunca llegó a registrarse, así que se puede enviarlo con esa misma referencia.

GET /orders?limit=50

Las órdenes de la cuenta, de la más reciente a la más vieja. limit va de 1 a 200 (50 por defecto).

{
  "ok": true,
  "total": 184,
  "truncated": true,
  "orders": [ { "external_id": "...", "sku": "...", "name": "...",
                 "game": "rb", "status": "COMPLETED", "price": "4.95",
                 "currency": "USD", "redeem_code": null,
                 "created_at": "2026-08-05T23:20:38.958Z" } ]
}

truncated indica si hay más órdenes de las que entraron en limit — una lista truncada sin avisar es indistinguible de una lista completa.

⚠️ Una orden ORPHANED no aparece en este listado: solo se ve consultándola por su referencia. Y el listado no pagina más allá de limit: para detectar un REFUNDED posterior a la compra hay que volver a consultar esa orden por referencia.

⚠️ Las órdenes anteriores a que existiera esta API tienen external_id y sku en null: no se hicieron por aquí.

8. external_id e idempotencia

La regla, en una línea: si no se sabe qué pasó con una orden, consultar — no reintentar.

⚠️ Si se ha trabajado con otras APIs del sector, no asumir su comportamiento. El nombre external_id es el mismo que usan otros proveedores de recargas, y cada uno hace algo DISTINTO al repetirlo: algunos rechazan la orden repetida con un error, otros devuelven la orden existente como si nada. Aquí ninguna de las dos: repetir un external_id resuelto devuelve la respuesta original completa (éxito O fallo, con "replay": true), una en vuelo da 409 OPERATION_IN_PROGRESS, y una que falló sin cargo permite reintentar con la misma referencia. La tabla de abajo es el contrato; lo aprendido en otra API no lo es.

Cada external_id identifica un pedido propio. Si se repite un POST /orders con una referencia ya usada, no se compra dos veces:

  • Si la primera se completó, se recibe la misma respuesta que entonces, con "replay": true agregado. Es seguro reintentar tras un timeout de red: o compra, o devuelve la compra que ya existía.
  • Si la primera falló antes de llegar al proveedor, la referencia se puede volver a usar.
  • Si la primera sí llegó al proveedor y no sabemos cómo terminó, se rechaza y hay que consultar el estado.

external_id_reusable — el campo a mirar ante un error

Todo error que decide la lógica de la orden lo trae en la raíz de la respuesta. Los que responde la capa de acceso antes de llegar a ella —401 UNAUTHORIZED, 429 RATE_LIMIT_EXCEEDED, 503 SERVICE_UNAVAILABLE de la clave y 400 INVALID_JSON— no lo traen, y no hace falta: en esos cuatro nada llegó a registrarse y la referencia sigue libre.

{ "ok": false, "code": "PLAYER_NOT_FOUND",
  "message": "La cuenta de usuario no es reconocida.",
  "external_id_reusable": true }
true cero cargo garantizado. Se puede corregir lo que estuvo mal (el ID del jugador, o incluso el sku) y reintentar con la misma referencia
false la orden llegó al proveedor. No reintentar con esta referencia — consultar GET /orders/{ref}

Un ID de jugador mal escrito es el caso típico de true: se corrige y se reintenta con la misma referencia, sin inventar una nueva.

La regla que hay detrás es una sola: la referencia es reutilizable si el intento nunca salió hacia el proveedor. Todo lo que se rechaza antes de enviar —saldo, precio, parámetros, un id inválido detectado en la validación previa— la deja libre. Todo lo que el proveedor ya recibió, no: repetirla devuelve la respuesta que ya hubo, con replay: true.

Estados

estado
COMPLETED entregada. Si el producto es de código, está en redeem_code
PROCESSING se está procesando. Consultar de nuevo; no reintentar el POST. En unos segundos si delivery.mode es instant; si es human, la orden espera a una persona — el bloque delivery de la orden dice si estamos fuera de horario y cuándo se retoma (resumes_at)
FAILED no se completó. No se cobró
REFUNDED se completó y el proveedor la revirtió después. El importe volvió al saldo de la cuenta

Y ORPHANED, que no es un estado de venta sino la excepción que pide intervención humana — ver las tres respuestas de GET /orders/{external_id} arriba.

9. Códigos de error

🔴 OUT_OF_STOCK significa disponibilidad, y nada más

Si una orden falla por una causa que no depende del producto —saldo insuficiente, id inexistente, cuenta restringida— se recibe ese motivo, con su propio código HTTP.

Importa porque la clase del código HTTP decide qué hacer:

acción
409 OUT_OF_STOCK esperar y reintentar más tarde
402 INSUFFICIENT_BALANCE recargar saldo
400 PLAYER_NOT_FOUND corregir el id con el usuario

Un 409 invita a reintentar; un 402 o un 400 dicen que reintentar sin cambiar nada va a fallar igual. Si el código del integrador ramifica por el código HTTP (=== 409), revisar que esos dos casos entren por otra rama.

Un mismo sku puede tener varios proveedores detrás, y normalmente probamos el siguiente cuando uno no puede servirlo. Ante estas causas no lo hacemos: el id no se vuelve válido cambiando de proveedor, ni el saldo alcanza más. Por eso el rechazo llega rápido en vez de después de probar con todos.

🔴 Antes de la tabla: qué significa "reintentar"

Para todo lo que devuelve POST /orders, la pregunta no es "¿puedo reintentar?" sino "¿puedo reintentar CON LA MISMA REFERENCIA?" — y esa la responde external_id_reusable, no esta tabla.

Nunca generar una referencia nueva para un pedido ya intentado. Es la única forma de comprar dos veces lo mismo. Si external_id_reusable viene false, la salida no es reintentar con otra referencia: es consultar GET /orders/{ref} y ver qué pasó.

La columna "¿reintentar?" de abajo asume siempre la misma referencia. Donde dice «según external_id_reusable» es porque el mismo código puede llegar antes o después de contactar al proveedor, y solo el campo lo sabe.

código HTTP ¿reintentar? (misma referencia)
UNAUTHORIZED 401 clave ausente, inválida, revocada o cuenta desactivada no
RATE_LIMIT_EXCEEDED 429 se superó el límite por minuto sí, tras RateLimit-Reset
INVALID_PARAMETER 400 un campo mal formado sí, corregido
INVALID_JSON 400 el cuerpo no es JSON válido sí, con el cuerpo corregido
SKU_NOT_FOUND 404 el sku no existe o dejó de venderse no
UNSUPPORTED_TYPE 400 en POST /orders: productos de monto libre (§7, GET /catalog), todavía no vendibles por API. En POST /verify-player: el producto es un código y no lleva id de jugador no
PLAYER_ID_REQUIRED 400 falta player.id sí, enviándolo
FIELD_REQUIRED 400 falta un campo de required_fields (cuál, en detail.field). No se cobró nada sí, enviándolo
FIELD_INVALID 400 un campo de fields no tiene la forma esperada (hoy: un tel que no es un teléfono de 9 a 15 dígitos). Cuál, en detail.field. No se cobró nada sí, corregido
PLAYER_NOT_FOUND 400 el ID de jugador no es reconocido según external_id_reusable: true si lo detectó la validación previa (lo normal), false si lo dijo el proveedor
ACCOUNT_RESTRICTED 400 la cuenta existe pero no puede recibir la recarga; el motivo del proveedor va en message no con ese id — tratarlo como permanente para esa cuenta
INSUFFICIENT_BALANCE 402 no alcanza el saldo. No se cobró nada sí, tras recargar
PRICE_CHANGED 409 el precio subió respecto del expected_price enviado sí, con el precio nuevo
OUT_OF_STOCK 409 ese sku no se puede servir en este momento según external_id_reusable: true si nadie pudo servirlo antes de enviar, false si un proveedor ya lo recibió
PROVIDER_REJECTED 502 rechazo no clasificado. El texto real va en message ⚠️ revisar external_id_reusable
OPERATION_IN_PROGRESS 409 ya hay una compra en curso con esa referencia no — consultar GET /orders/{ref}
ORPHANED 409 quedó a mitad, necesita revisión manual no — escribir a soporte
ORDER_NOT_FOUND 404 no hay ninguna orden con esa referencia —
ROUTE_NOT_FOUND 404 la ruta no existe en la API v1 (con una clave válida; sin clave, toda ruta responde 401) no — revisar la URL
SERVICE_UNAVAILABLE 503 no pudimos verificar la clave en este momento (problema nuestro, transitorio). En POST /verify-player significa otra cosa: no se pudo consultar al proveedor sí — respetar Retry-After
INTERNAL_ERROR 500 problema nuestro ⚠️ revisar external_id_reusable

503 no es 500

Un 503 SERVICE_UNAVAILABLE significa que no pudimos verificar la clave en este momento — se despeja solo, normalmente en segundos. Viene con Retry-After y reintentar es lo correcto: ninguna orden llegó a procesarse, así que la referencia sigue libre.

Un 500 INTERNAL_ERROR es un problema nuestro sin garantía de ser transitorio. Si aparece en POST /orders, revisar external_id_reusable antes de hacer nada.

⚠️ PROVIDER_REJECTED y INTERNAL_ERROR no se pueden resolver desde la tabla, y son los dos donde equivocarse cuesta dinero. Agrupan lo que no pudimos clasificar, y algunos de esos casos ocurren después de que la orden salió a procesarse: ahí external_id_reusable viene false y la salida es consultar, no reintentar.

Ramificar por el campo, no por el código. Si la integración solo va a mirar una cosa ante un error de POST /orders, que sea external_id_reusable.

⚠️ PLAYER_NOT_FOUND y ACCOUNT_RESTRICTED son distintos a propósito. El primero significa "ese número está mal, hay que corregirlo"; el segundo, "el número está bien, pero esa cuenta no puede recibir la recarga". Tratarlos igual manda al cliente a revisar un ID que ya estaba correcto.

PROCESSING y OPERATION_IN_PROGRESS NO son lo mismo

Se parecen y aparecen en momentos distintos:

dónde aparece qué es qué hacer
PROCESSING como status de una orden, con "ok": true la compra se está procesando ahora esperar unos segundos y volver a consultar
OPERATION_IN_PROGRESS como code de un error 409, con "ok": false se envió un POST con una referencia que ya tiene una compra en curso no reintentar el POST: consultar GET /orders/{ref}

La forma de distinguirlos en código es directa: PROCESSING viene con ok: true y dentro de order.status; OPERATION_IN_PROGRESS viene con ok: false y en code.

El segundo no es un fracaso: es la API indicando que ya recibió ese pedido y lo está procesando. La compra sigue viva.

10. Flujo recomendado

1.  GET /catalog               (una vez al día, o cuando se desee refrescar)
        └─ guardar sku, nombre y requires_player_id

2.  Al vender:
        GET /catalog/{sku}     ← si se necesita el precio exacto
        └─ revisar price_is_estimated

3.  POST /orders  con el external_id propio y expected_price
        ├─ 200 + COMPLETED  → entregar `redeem_code` (o confirmar la recarga)
        ├─ 200 + PROCESSING    → consultar GET /orders/{ref} en unos segundos
        ├─ error con external_id_reusable: true   → corregir y reintentar con LA MISMA referencia
        ├─ error con external_id_reusable: false  → GET /orders/{ref}, NO reintentar
        └─ timeout / sin respuesta                   → GET /orders/{ref}, NO reintentar

Dos cosas que evitan casi todos los problemas de integración:

  1. Una external_id propia y única por pedido, siempre — y la misma en cada reintento de ese pedido. Es lo que hace seguro reintentar y lo que permite consultar qué pasó. Generar una referencia nueva para un pedido ya intentado es la única forma de comprar dos veces lo mismo.
  2. Ante cualquier incertidumbre, consultar antes que reintentar.
